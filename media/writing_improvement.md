Comprehensive Evaluation Strategy

Evaluating an agentic RAG system for manufacturing support must verify more than final answer fluency. The protocol has to measure source retrieval quality, factual correctness of generated claims, consistency between intermediate reasoning and final output, and robustness under local execution constraints. This framework evaluates the full system path from retrieval to synthesis while keeping each result traceable to the indexed manuals and image artifacts used during inference. This design was necessary because the system answers both text only questions and questions that require text and images in the same response, which introduces scoring challenges that are not captured by surface text similarity alone.

Benchmark Dataset Design

The benchmark is derived from equipment manuals indexed in the local FAISS based RAG store, and it contains fifty questions split evenly between text only and text with image requirements. Each sample includes the query, the expected source manual, and a reference answer so that correctness and source grounding can be evaluated jointly. During execution, each sample runs through the full agent process with tool registration, retrieval calls, iterative reasoning, and final answer synthesis, rather than isolated component tests. This setup makes the benchmark representative of deployed behavior because it evaluates the same pipeline used in normal operation.

Traditional NLP metrics (Lexical and Semantic Evaluation)

BLEU, ROUGE, token F1, and BERTScore were useful in early iterations, but they are not the active benchmark method in the presented system because the primary failure mode of this agent is not wording mismatch, it is evidence mismatch. BLEU, ROUGE, and token F1 emphasize token overlap between generated and reference text, while BERTScore computes embedding similarity between those two strings. This framing becomes unstable for multimodal manufacturing answers, where correct outputs often include local image markdown links, filenames, page references, and concise operational language that can differ from the wording style of the reference answer while remaining technically correct. In these cases, lexical metrics may drop because the model surfaces the right local figure from the companion image repository but expresses it with different phrasing or link text, which creates low overlap without a real grounding error.

The same limitation appears when image context enters the answer through artifacts generated in the companion pipeline. The second repository builds image_index.json with per-image metadata, image_embeddings.npy with vector representations, and embedding_mapping.json with index to filename mapping, then this project retrieves those assets and injects valid local links into final responses. Classical metrics do not understand that this link insertion is required product behavior, so they may punish responses for including URLs and markdown tokens that are semantically irrelevant to factual quality. For this reason the benchmark runner cleans response text before judging by removing image markdown, converting links to anchor text, stripping formatting tokens, and normalizing whitespace. That cleanup is methodologically necessary because it prevents markup artifacts from dominating the score and ensures the evaluation focuses on claim content, source alignment, and query resolution quality. Under this evaluation goal, lexical metrics remain useful as secondary language quality indicators, but they are not sufficient as primary criteria for a multimodal agent where correctness depends on grounded evidence rather than phrasing similarity.

LLM-as-Judge Evaluation (RAGAS Framework)

The active evaluation is implemented with RAGAS and uses four metrics, namely context recall, faithfulness, factual correctness, and answer relevancy, because these target the exact risk profile of retrieval-augmented agent systems. For each benchmark sample, the runner constructs a structured judge payload containing user_input, retrieved_contexts extracted from the reasoning tree, response, and reference, then sends that payload to a local judge stack. The judge LLM is served through Ollama and is controlled by RAGAS_JUDGE_MODEL with hf.co/bartowski/Meta-Llama-3.1-8B-Instruct-GGUF:Q4_K_M as default, so all judgment stays local and reproducible. The response relevancy component uses local embeddings from all-MiniLM-L6-v2, which means sentence meaning comparisons are computed as vector geometry in local embedding space rather than keyword overlap; this is relevant because the same intent can be expressed with varied terminology, especially in maintenance language.

Each RAGAS metric captures a distinct quality dimension. Context recall asks whether the retrieved context set actually contains the information needed to answer the question, so low values usually indicate retrieval miss or missing evidence coverage before generation even starts. Faithfulness asks whether statements in the final answer are inferable from retrieved context, so low values signal hallucination or overextension beyond available evidence. Factual correctness asks whether final claims agree with reference facts, which captures factual drift even when retrieval looked plausible. Answer relevancy asks whether the output addresses the user query directly instead of producing technically correct but off-target content. Together these four scores separate retrieval failure, grounding failure, factual failure, and relevance failure, which is exactly what lexical metrics cannot disentangle.

Score interpretation in the runner is transparent and metric-wise, with 0.90 to 1.00 treated as excellent near-perfect behavior, 0.70 to 0.89 treated as good, 0.50 to 0.69 treated as acceptable but improvement-needed, and below 0.50 treated as poor to bad depending on severity. A literal perfect 1.00 is possible but uncommon in practical runs, so the decision criterion is sustained high scores across all four dimensions rather than a single peak number. This is the strongest reason to use RAGAS in this project: it evaluates whether the system retrieved the right evidence, grounded claims in that evidence, remained factually correct, and answered the actual question under multimodal conditions where wording-level overlap is not a reliable proxy for correctness.

Visual Grounding Evaluation

The visual retrieval process consumes three key local artifacts produced by the companion image pipeline: image_index.json, image_embeddings.npy, and embedding_mapping.json. The image_index.json file stores per image metadata such as source manual, page location, and descriptive text. The image_embeddings.npy file stores dense numeric vectors for semantic image lookup. The embedding_mapping.json file maps each embedding row to the corresponding image filename and metadata record, which lets the system convert similarity ranking into resolvable image references. At runtime, the backend mounts local image files under /api/media/yologen and returns links in the answer using markdown with URLs such as ![description](http://localhost:8000/api/media/yologen/train/APSX-PIM_page41_img1.png). Because these links are required for correct user facing output, the benchmark pipeline cleans responses before scoring by removing image markdown and normalizing formatting so the judge evaluates factual content instead of markup noise.

Multimodal Consistency and Joint Synthesis

Multimodal consistency in this system is enforced by combining manual retrieval evidence and image retrieval evidence within one reasoning graph and one final response, so each claim can be traced to either text chunks, image metadata, or both. The text retrieval path uses FAISS for fast first-stage candidate search and then a cross-encoder reranker, specifically ms-marco-MiniLM-L-6-v2, to rescore query-chunk pairs with finer interaction modeling. This cross-encoder stage is fundamental because it reduces false-positive chunks that look similar in vector space but are contextually weak for the exact maintenance query. In parallel, image retrieval uses sentence-transformer embeddings from all-MiniLM-L6-v2 over VLM-enriched image descriptions generated in the companion repository, which allows semantically aligned image lookup rather than filename matching. The synthesis layer then merges these ranked text and image signals, preserves valid local image links, injects omitted but retrieved links when needed, and filters hallucinated links that do not match the mounted local media endpoint, maintaining end-to-end evidence traceability.

Making this pipeline run fully offline required resolving concrete dependency failure modes. Early offline runs failed when semantic models were not already cached and libraries attempted remote model resolution, which can silently occur for sentence-transformer and cross-encoder loads if cache artifacts are missing. Additional failures appeared when image embedding artifacts were partially present, for example index without matching embedding mapping, producing incomplete semantic image retrieval initialization. The current process addresses these issues through strict offline mode gates, startup prerequisite validation, and explicit cache warmup scripts for sentence-transformers/all-MiniLM-L6-v2 and cross-encoder/ms-marco-MiniLM-L-6-v2 before runtime. This architecture is critical for industrial deployment because it eliminates reliance on external API tokens, removes OpenAI or Mistral service dependencies, keeps Ollama-based judging and generation local, and ensures that operational prompts, retrieved evidence, and generated outputs remain on local infrastructure rather than being transmitted to external providers.
